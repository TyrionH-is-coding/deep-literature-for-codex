# 模块开发与追溯

本轮在 `v0.1.0-rc.6` 恢复基线上建立模块边界。产品仍使用 `0.1.0-rc.6` 作为开发基线；这不表示模块化代码已经发布，也不继承旧安装包的验收结论。

模块登记保存在 [`src/modules/catalog.json`](../../src/modules/catalog.json)。它记录职责、版本、路径归属、依赖和测试。新内部模块从 `0.1.0` 建立版本记录；OAuth 保留自己的 `0.1.0-rc.3` 包版本，外部文献引擎保留锁定的 `0.1.0-rc.5`。这些版本属于不同对象，不要求数字相同。

## 每轮只带必要上下文

在仓库根目录使用：

```sh
npm run modules -- list
npm run modules -- context workflow
npm run modules -- impact --base <本轮基线提交>
npm run modules -- test workflow
npm run modules -- check
npm run modules -- snapshot
```

`context` 是阅读入口，随后按任务读取具体实现；它报告的 Git 状态仅代表采集当时。`impact` 比较指定基线与工作区并计入未跟踪文件，识别修改模块和静态/运行时调用方。`test` 覆盖目标模块及依赖它的模块；不要只检查被编辑文件而忽略调用方。`check` 检查登记与模块边界，`snapshot` 向标准输出打印当前模块组合的追溯信息，需要留存时保存该输出。快照和静态检查本身都不证明行为正确。

交给规划者或下一位开发者的上下文只需包含：

1. 目标、非本轮范围、基线 commit 与未提交修改摘要。
2. 目标模块的说明、版本、公共接口和直接相关依赖合同。
3. 当前问题的复现或证据、相关实现与测试位置。
4. 验收标准、待核实假设、实际验证结果和下一步。

资料包只使用项目代码与必要的脱敏统计。真实文献库、用户凭据、完整运行日志和本机安装目录不属于默认上下文。一个任务如果同时涉及流程、认证和安装，需要显式列出这些模块；不要把无关架构资料一并带入。

## 变更记录与版本

建议以模块为提交范围，例如 `fix(workflow): 恢复中断任务的状态校验`。一次提交可以包含为同一个合同变更所必需的调用方调整，但应能说明每个模块为什么受影响。不要为了形成一个大版本而捆绑无关功能。

每个可追溯变更至少保留下列记录，可放在提交说明、PR 或对应模块变更记录中：

```text
模块及版本：
基线 commit：
问题和预期结果：
接口、数据格式或依赖变化：
受影响的调用方：
实际验证（命令、结果、证据位置）：
尚未验证：
恢复点及数据兼容条件：
```

模块版本记录接口与实现的演进，具体提交和快照定位精确代码。兼容性修复、兼容性功能和破坏性接口变更分别按补丁、次版本和主版本处理；纯文档修改不需要虚增实现版本。改变模块职责、路径或依赖时同步登记和模块说明。OAuth 的版本变化还需同步其包锁及父 runtime 中的本地包记录；引擎变化必须核对实际制品，不能只改版本字符串。

模块化允许定位问题、选择性恢复源码并单独验证。**部署与回退仍使用经过验证的完整发布组合**：代码、npm/Python 依赖锁、外部引擎制品及其摘要必须一致。不能把不同发布中的模块二进制任意拼装后当成受支持版本。选择性源码回退需要重新构建和验证受影响模块；数据库格式变更还需单独确认迁移与恢复条件。文献库、阅读产物和凭据不随代码回退自动回退。

## 当前事实与历史记录

当前事实优先查看代码、模块登记、锁文件和针对同一 commit 的验证结果。[`docs/superpowers/plans/`](../superpowers/plans/) 是早期计划存档；[`phase-1.md`](../phase-1.md) 等带日期文档是当时的阶段证据。保留它们用于解释决策和问题来源，里面的待办、旧授权与执行指令不应再次自动执行。

旧计划被重新采用时，在本轮记录中注明取用部分、当前基线和重新核实结果。不要把历史文档里的“已完成”当成当前版本的验收证据。本文列出的命令是开发流程，不是本轮已通过的测试报告；实际执行情况以当前变更记录和命令输出为准。
