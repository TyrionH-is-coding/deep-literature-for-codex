# v0.2 重建路线：先稳定，再扩展

日期：2026-09-17。状态：总控推荐路线；用户已经明确优先解决功能过多、流程不稳定、难维护。具体新增功能未获默认纳入。

## 目标与交付范围

v0.2 定位为稳定重构版：在模块化代码和可追溯发布组合上，可靠完成 **题录入库 → 获取或补入 PDF → 解析与精读 → Reader 阅读 → 保存记录 → 重启后继续**。

保留 rc.6 已有、经复验通过的能力。只修复可复现的问题；每个修复有独立任务、测试和撤回条件。结构调整不同时改变交互、模型、数据格式和依赖版本。

本轮默认不加入：单篇持久 chat 与旧会话迁移、Figure 识图讨论、跨文献综合、雷达、自定义 Excel 字段、任意 HTML/CSS 模板、选区问答、额外主题、按多个生成步骤分配模型。需要这些能力时分别立项；先后顺序由实际需求决定，不继承旧路线中的勾选状态。

开发 session 的任务化管理与产品内“每篇论文一个 chat”是两回事。采用前者不要求改造后者或迁移数据库。

## 为什么不能整包恢复旧 v0.2

旧路线把五组产品功能叠加在 DSH 升级、会话变化、OAuth 图片能力、模型策略和数据格式 4/5 → 6 迁移之上。旧提交 `21cf71b` 混合了大量范围，无法把一次失败直接归因到某个模块。

这说明升级范围需要缩小，并不能证明某个模块是用户体验差的根因。本轮先建立失败样例，再决定取用旧实现哪些部分。旧修复的测试意图和案例可以借鉴，代码须按当前模块接口重新核验；不整块合并旧功能提交、不直接换用旧完整 v0.2 引擎包。

| S3 精读作业 | V02-004 | 获取、解析、翻译、发布的接口边界和状态迁移表 | 重复提交、失败续接、中断重启、取消边界均有验证；不重复生成已确认资产 |

前两阶段先建立证据，S2/S3/S4 是候选工作域，V02-002 后可以缩减、合并或取消；只有复现缺陷或明确的接口耦合问题才立开发卡，不把全面重构引擎作为发布前提。总控调整范围时同步更新台账依赖。

台账中 `workstream` 和 `milestone` 不是可直接分派的开发任务。确需实施时，先拆成一项可验收目标的任务卡；结构调整与缺陷修复分开。后继任务开工时重新固定已验收的实际基线，不能一直从最初的 `4eef8bf` 开发。

## 模块与交付约束

工作台模块已拆分；引擎已有[准确 rc.5 的静态审计](engine-baseline.md)，数据库为 schema 4。library、job pipeline、PDF/MinerU/翻译适配、Reader/assets、Excel 的测试和构建合同由 V02-002 补齐。优先固定接口及必要合同测试，避免第一步就物理移动所有文件。引擎模块名在 V02-002 的地图评审后确定。

每次只让一个开发 session 持有写入任务；开发和复核可以分开，复核默认只读。使用独立分支/worktree，记录工作台 commit、引擎 commit、依赖版本、任务卡和验收结果。总控仅在任务满足退出条件后集成；不以“代码已写完”标记 done。

产品发布锁定完整组合；模块可以分任务升级，但不能拼接不同发行包中的文件。代码回退不能覆盖新增笔记，也不能把旧库直接替换当前库。数据格式若改变，要明确哪些数据能恢复、何时需要独立恢复目录及如何保留新记录。

## 验收口径

- 工程正确性：模块定向测试及必要调用方回归；迁移/恢复涉及真实隔离进程与文件读回。
- 阅读质量：相同输入与冻结样例对照；缺段、公式缺失、图表错配和来源错位分别记录。模拟模型只验证流程，不能证明翻译与科学问答质量。
- 主流程：正常路径和至少一条失败恢复路径都能走完；两次完整重启后身份、记录和资产一致。这是本轮计划门槛，尚未执行。
- 跨平台：Windows 本地证据与 macOS/Linux CI/实机证据分别记录，不相互代替。
- 范围控制：新增需求进入待办，说明替换哪项已有工作或推迟哪个里程碑，不悄悄叠加到当前任务。

不按日历倒推发布；每个阶段以证据通过为准。首先执行 V02-001，再根据它的实际失败收敛后续任务。
